# 실패 단계부터 다시 · 배포 되돌리기 (5-2)

## 1. 실패 단계부터 다시

지금까지 [다시 시도]는 일감을 처음부터 다시 했다. 실패한 단계가 기록돼 있으면 [실패 단계부터 다시]가 함께 나온다.

| 부분 | 내용 |
|---|---|
| 서버 | `lib/factory/stageRetry.ts` — 새 앱·수정 일감, 상태 `failed`, `failStage` 기록 있음, 단계가 `resume`(이어받기 자체 실패)이 아닐 때만. 누르면 `approved` 로 되돌리고 `resumeFrom`(단계)·`resumeNote`(실패 이유, 비밀번호 마스킹·500자)를 남긴다. 관리자 동작 `retry-stage`. 일반 `retry` 는 두 값을 지우고 처음부터 |
| `/next` | 단계부터 다시 승인된 일감에 `stageResume: { from, note, label }` 이 붙는다 |
| 감독 프로그램 | `stageresume.mjs` — 새 앱·수정 일감이 실패하면 AI 세션을 작업 폴더 `.factory/sessions/<일감id>.json` 에 기억한다(세션 id·AI·단계·시각, 비밀값 없음). 단계 재개 요청이 오면 같은 세션(`--resume` / `exec resume`)에 "이전 시도가 '검사' 단계에서 실패했다. 오류: …. 이 오류만 고치고 그 단계부터 이어서 마무리해" 짧은 지시만 넣는다 |
| 대체 동작 | 작업 폴더·세션 기록이 없거나, 다른 일감 기록이거나, AI 가 다르거나(Claude↔Codex), 3일보다 오래됐거나, 병행(작업 사본) 일감이거나, 이어서 하기가 바로 오류로 끝나면 → 기존 재실행(처음부터 지시문)으로 대신한다. 이유는 일감 로그에 남는다 |
| 단계 이름 | 검사 실패는 `check`, 그 밖에는 AI 가 `.factory/phase.txt` 에 쓴 단계(`scaffold`·`build`·`screenshots` 등) 또는 `merge`·`stuck`. 출시 일감은 따로 있는 출시 화면의 단계 재시도를 쓴다 |

## 2. 배포 되돌리기

통제실 [현황] → 업데이트·배포 이력 → [서버 배포] 줄에 성공한 배포마다 **[↩ 이전 버전으로]** 가 있다(통제실에서만, 텔레그램 버튼 없음).

흐름(기존 배포 경로 그대로, force push 없음):

1. 서버가 조건을 검사하고 `deployCommit=대상`, `deployRevertTo=대상` 으로 배포를 요청한다. `FactoryDeploy(kind=revert)` 한 줄 + 텔레그램 "되돌리기를 시작해요".
2. 감독 프로그램이 `/next` 의 `maintenanceDeploy.revertTo` 를 받으면 `deploy_start` 를 알리고, 정비 폴더에서 **되돌리기 커밋**을 만든다(`revert.mjs`).
   - 부모 = 지금 GitHub main, 내용 = 대상 커밋의 내용. 임시 index 로 트리만 만들어 `git commit-tree` 로 커밋하고 `git push origin <커밋>:refs/heads/main`(보통 push, 빨리감기). 거절되면 그대로 실패.
   - `tools/factory-supervisor` (감독 프로그램 코드)는 지금 것을 그대로 둔다. 홈페이지 배포와 따로 GitHub 에서 업데이트되는 코드라서.
   - 이미 같은 내용이면(지난번에 만들고 보고만 못 한 경우) 새 커밋 없이 지금 main 을 쓴다.
3. `deploy_revert_commit` 으로 서버에 새 커밋을 알리면(서버가 배포 커밋을 그 커밋으로 바꿈) 그 뒤는 평소 배포와 같다: 서버 배포 저장소로 push → 빌드·교체 → 헬스체크 → `deploy_done` → 텔레그램 "되돌리기 완료/실패".
4. 못 만들면(마이그레이션·정비 폴더 변경 등) 배포 저장소에 아무것도 올리지 않고 `deploy_done(ok=false)` 로 이유를 보고한다. 서버는 그대로다.

### 막는 조건 (이유가 화면에 표시된다)

- 성공한 배포만, 지금 서버에 올라간 버전은 제외.
- 배포 진행 중 / 정비 대기열이 남음 / 아직 배포하지 않은 정비 변경이 있음(되돌리면 그 변경도 같이 사라지므로).
- **DB 마이그레이션이 든 배포가 대상과 지금 사이에 있음.** 서버가 배포마다 감독 프로그램이 알려 준 `FactoryDeploy.migrations`(앞선 배포 대비 `prisma/migrations` 변경 여부)로 미리 판단하고, 값이 없는(예전) 배포는 통과시킨 뒤 감독 프로그램이 실제 git 차이(`대상..지금 main`)로 한 번 더 막는다. 마이그레이션은 되돌리지 않는다. 고칠 점은 새 정비 지시로 보낸다.

### 데이터

마이그레이션 `20261118110000_deploy_revert` — 칸만 추가(`factory_maintenance.deployRevertTo`, `factory_deploys.kind/revertTo/migrations`), 기존 데이터를 지우지 않는다.

### 한계

- 되돌리기 직후 정비 폴더 main 도 되돌리기 커밋까지 따라간다. 이전 정비 커밋은 기록에 그대로 남는다(되돌리기 커밋이 위에 쌓일 뿐).
- 감독 프로그램 코드는 되돌리지 않는다. 홈페이지 API 가 바뀌어 감독 프로그램과 어긋나면 별도 정비로 맞춘다.
- 배포 중 서버가 20분 넘게 결과를 못 받으면 기존처럼 실패로 정리된다.

## 3. 앱 배포(prod 원격 등)에도 같은 방식을 쓸 수 있나 — 보고만 (이번 범위 아님)

1-6 연결 정보(`factory_app_connections`, `lib/factory/projectLinks.ts`)에는 앱별 git 원격(목적: 백업·배포·GitHub), 배포 서버(serverpc/serverpc2/none), 도메인, 컨테이너 이름, 배포 방법(자유 입력 100자)이 있다. 같은 "되돌리기 커밋 + 배포 원격 push" 기법은 **배포 방법이 "배포 원격에 push" 인 앱**에만 기술적으로 쓸 수 있다. 하지만 지금은:

1. 앱 배포 이력(어떤 커밋을 언제 배포했는지, 결과)이 어디에도 기록되지 않는다(연결 정보는 현재 상태 기록일 뿐).
2. 배포 방법이 통일돼 있지 않고 자유 입력이라, 감독 프로그램이 "어떤 명령으로 올리는지"를 기계적으로 알 수 없다.
3. 앱마다 DB(Prisma·NestJS 등)와 마이그레이션 위치가 달라 "마이그레이션이 든 구간" 판단 기준이 없다.
4. prod 원격은 출시 일감·사람이 직접 push 하는 경로가 섞여 있다.

따라서 먼저 (1) 앱 배포 이력 기록 칸, (2) 배포 방법 종류 고정(git push 형 등), (3) 앱별 마이그레이션 경로 설정이 필요하다. 그 뒤에는 `revert.mjs` 의 `buildRevertCommit` 을 앱 폴더·배포 원격으로 일반화하면 된다.
